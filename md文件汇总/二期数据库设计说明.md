# AI API 项目二期数据库设计说明

## 1. 文档目标

本文档基于 [二期需求.md](./二期需求.md) ，补齐二期落地所需的数据结构设计，重点覆盖：

- 总需求 / 子需求树形模型
- Agent 会话管理
- 客户端节点与本机 Agent 能力上报
- 基于 WebSocket 的服务端主动派发任务
- 项目 Markdown 列表化管理增强
- Markdown 同步冲突记录

本文档不是最终 DDL，但已经足够作为二期建表和 Flyway 迁移设计的直接输入。

---

## 2. 设计原则

### 2.1 兼容一期

二期应建立在一期现有表结构之上，尽量通过：

- 增字段
- 增索引
- 增新表

来完成扩展，而不是推翻一期结构重做。

### 2.2 保留“主单 + 执行记录”双层模型

二期很多对象既有“当前状态”，也需要“历史轨迹”，因此设计上遵循：

- 主表记录当前聚合状态
- 事件表 / 记录表保留过程明细

### 2.3 优先支持查询与追踪

二期不是只要“能存”，还要能支撑：

- 查询某总需求下全部子需求
- 查询某 Agent 可复用会话
- 查询某台电脑上的可用 Agent
- 查询某个派发任务的全链路执行历史
- 查询 Markdown 冲突记录

因此会适当保留冗余字段，例如：

- `root_requirement_no`
- `project_code`
- `client_code`

这些字段在部分表中虽然可间接推导，但直接保存更利于查询和审计。

### 2.4 通信层优先选择 WebSocket

二期通信层默认选择 WebSocket，而不是原始 TCP 套接字。

数据库设计因此遵循两点：

- 业务表尽量与底层传输协议解耦
- 仅在客户端节点表中保存少量连接态字段，用于追踪当前 WebSocket 会话

## 5. 一期表结构增强

## 5.1 项目表 `project_info`

一期已存在：

- `project_code`
- `project_name`
- `project_desc`
- `business_goal`
- `tech_stack`
- `repository_url`
- `owner_agent_code`
- `markdown_sync_mode`
- `status`

二期建议：

- 保留 `markdown_sync_mode` 作为项目默认同步策略
- 不再把 Markdown 管理理解为“单块配置”，而是配合 `project_markdown_file` 做列表管理

索引建议：

- 保留 `uk_project_code`

说明：

- 该表本身无需为二期新增大量字段
- Markdown 是否参与同步、排序、摘要等细粒度属性放在 `project_markdown_file`

## 5.2 项目 Markdown 文件表 `project_markdown_file`

一期字段基础上建议增强为：

- `id`
- `project_code`
- `file_type`
- `base_key`
- `file_path`
- `content`
- `sync_enabled_flag`
- `display_order`
- `content_hash`
- `created_at`
- `updated_at`

字段说明：

- `sync_enabled_flag`
  - 是否参与客户端同步
- `display_order`
  - 页面展示顺序
- `content_hash`
  - 用于快速比较是否发生变化

约束建议：

- `UNIQUE (project_code, file_path)`
- 基础文件建议保留 `UNIQUE (project_code, base_key)`

索引建议：

- `idx_project_markdown_project_type (project_code, file_type, sync_enabled_flag)`

说明：

- 二期要求“md 文件改为列表”，这张表是核心支撑表
- 基础文件和额外文件统一落在同一张表，避免拆成两张维护

## 5.3 需求表增强 `requirement_info`

在一期基础上新增字段：

- `requirement_type` `VARCHAR(16)`，非空，默认 `MASTER`
- `parent_requirement_no` `VARCHAR(64)`，可空
- `root_requirement_no` `VARCHAR(64)`，非空
- `sort_no` `INT`，默认 `0`
- `session_strategy` `VARCHAR(32)`，可空
- `preferred_session_code` `VARCHAR(64)`，可空

字段含义：

- `requirement_type`
  - 标记该记录是总需求还是子需求
- `parent_requirement_no`
  - 子需求的父需求编号
- `root_requirement_no`
  - 总需求编号
- `sort_no`
  - 子需求在父需求下的顺序
- `session_strategy`
  - 该需求默认派发时采用的会话策略
- `preferred_session_code`
  - 用户手工指定的优先复用会话

索引建议：

- `idx_requirement_root_sort (root_requirement_no, sort_no, status)`
- `idx_requirement_parent_sort (parent_requirement_no, sort_no)`
- `idx_requirement_project_root (project_code, root_requirement_no)`

数据规则：

- 总需求：
  - `requirement_type = MASTER`
  - `parent_requirement_no = NULL`
  - `root_requirement_no = requirement_no`
- 子需求：
  - `requirement_type = SUB`
  - `parent_requirement_no != NULL`
  - `root_requirement_no = 所属总需求编号`

## 6.2 会话表 `agent_session`

该表是二期核心表之一，用于管理 Agent 会话生命周期。

建议字段：

- `id`
- `session_code`
- `session_name`
- `session_type`
- `project_code`
- `requirement_no`
- `root_requirement_no`
- `agent_code`
- `client_code`
- `external_session_id`
- `status`
- `reusable_flag`
- `last_active_time`
- `created_at`
- `updated_at`

字段说明：

- `session_type`
  - 可区分 `CODEX_CLI`、`QODER_CLI`、`CLAUDE_CODE`
- `external_session_id`
  - 第三方 CLI 自身的会话标识
- `reusable_flag`

索引建议：

- `idx_session_project_agent (project_code, agent_code, last_active_time)`

由于一个需求后续可能出现多个历史会话，因此建议单独建绑定表，而不是只依赖 `preferred_session_code`。

- `binding_type`

- `remark`

字段说明：

- `binding_type`

  - `HISTORY`
  - `AUTO_SELECTED`
- `is_primary_flag`
  - 当前需求默认优先使用的会话

索引建议：

- `idx_req_session_req (requirement_no, is_primary_flag, created_at)`
- `idx_req_session_session (session_code, created_at)`

用于登记接入系统的电脑节点。

建议字段：

- `id`

- `client_name`
- `os_type`
- `host_name`
- `ip_address`
- `connection_protocol`
- `connection_session_id`
- `status`
- `last_heartbeat_time`
- `supported_agent_types`
- `app_version`
- `created_at`
- `updated_at`

字段说明：

- `client_code`
  - 客户端唯一标识，建议服务端生成或注册时约定

## 6.5 客户端 Agent 能力表 `client_agent_runtime`

用于记录某台电脑上有哪些 CLI Agent 可用。

建议字段：

- `id`
- `client_code`
- `agent_type`
- `agent_name`
- `agent_version`
- `command_path`
- `available_flag`
- `capability_tags`
- `supports_session_reuse`
- `default_workspace_dir`

索引建议：

- `idx_runtime_agent_type_available (agent_type, available_flag)`

## 7. 表关系说明

核心关系建议如下：

- `project_info 1 --- n requirement_info`
- `project_info 1 --- n project_markdown_file`
- `project_info 1 --- n project_markdown_sync_conflict`
- `requirement_info(总需求) 1 --- n requirement_info(子需求)`
- `requirement_info 1 --- n requirement_session_binding`
- `agent_session 1 --- n requirement_session_binding`
- `client_node 1 --- n client_agent_runtime`
- `client_node 1 --- n dispatch_task_record`
- `agent_session 1 --- n dispatch_task_record`
- `dispatch_task_record 1 --- n dispatch_task_event`

说明：

- `requirement_session_binding` 和 `dispatch_task_record` 同时存在是合理的
- 前者解决“需求历史上绑定过哪些会话”
- 后者解决“这次具体派发实际用了哪个会话”

## 9. 数据一致性规则

### 9.1 需求层级

- 子需求插入时必须校验父需求存在
- 子需求与父需求必须属于同一 `project_code`
- 子需求的 `root_requirement_no` 必须等于父需求的 `root_requirement_no`

### 9.2 会话复用

- `REUSE_SELECTED` 时，必须校验 `preferred_session_code` 存在且 `reusable_flag = true`
- `REUSE_LATEST` 时，应优先按：
  - `agent_code`
  - `project_code`
  - `root_requirement_no`
  - `last_active_time desc`
  进行匹配

### 9.3 客户端可用性

- `dispatch_task_record` 创建前，目标 `client_code` 必须在线
- 目标客户端对应的 `client_agent_runtime` 必须存在且 `available_flag = true`

### 9.4 WebSocket 连接替换规则

- 同一 `client_code` 重连时，新的 `connection_session_id` 应覆盖旧值
- 服务端只应以最新在线的 `connection_session_id` 作为主动派发目标
- 若连接断开，应及时将 `client_node.status` 更新为 `OFFLINE`

### 9.5 Markdown 同步

- 只有 `sync_enabled_flag = true` 的 Markdown 文件参与同步
- `CANCEL` 模式发生冲突时，必须插入 `project_markdown_sync_conflict`

## 10. 二期与一期兼容建议

### 10.1 接口兼容

- 一期已有 `requirementNo` 仍可继续使用
- 若未传 `requirement_type`，默认按一期逻辑视为总需求

### 10.2 数据兼容

对一期已有需求数据，可按以下方式初始化：

- `requirement_type = MASTER`
- `parent_requirement_no = NULL`
- `root_requirement_no = requirement_no`
- `sort_no = 0`

### 10.3 Markdown 兼容

一期项目 Markdown 配置迁移到二期时：

- 原基础文件记录继续保留
- 新增字段默认：
  - `sync_enabled_flag = 1`
  - `display_order` 按基础文件顺序初始化

## 11. 当前建议结论

当前二期数据库设计里，最关键的不是“多几张表”，而是三个中心对象明确下来：

1. `requirement_info`
   - 从单层需求升级为树形需求
2. `agent_session`
   - 把会话正式变成平台对象
3. `dispatch_task_record`
   - 把服务端主动派发正式建模

只要这三个对象设计正确，客户端上报、历史会话复用、跨电脑协作、Markdown 同步追踪就都能自然接上。
