# AI API 项目二期需求说明

## 1. 二期目标

配套文档：

- [二期数据库设计说明.md](./二期数据库设计说明.md)
- [二期接口文档.md](./二期接口文档.md)

二期不是简单补几个页面，而是把一期的“多 Agent 协同任务中台”继续往前推进，增强成一个 **支持分层需求、会话复用、任务主动下发、跨电脑协同** 的多智能体分布式协同系统。

二期核心目标：

- 项目级 Markdown 配置从“编辑内容”升级为“文件列表化管理”
- 需求模型从单层需求升级为“总需求 + 子需求”树形结构
- Agent 增加会话管理，任务下发时可以选择“沿用旧会话”或“新建会话”
- 新增 Python 客户端模块，通过 WebSocket 与服务端长连接，实现服务端主动派发任务
- 服务端能够感知每台电脑上有哪些可用 CLI 智能体，并按能力进行分配
- 支持 macOS 和 Windows 两端接入

---

## 2. 二期定位

如果说一期的重点是“把协作数据落表、把最小闭环跑起来”，那么二期的重点是：

1. 让需求结构更贴近真实研发管理
2. 让会话上下文可以持续复用
3. 让任务不再只靠轮询，而是支持服务端主动推送
4. 让系统具备跨设备、跨 Agent 的分布式协同能力

因此，二期本质上是从“任务中台”往“分布式 Agent 调度平台”演进。

---

## 3. 二期范围

### 3.1 二期必须具备

1. 项目 Markdown 文件列表化管理
2. 总需求 / 子需求层级管理
3. 需求与 Agent 会话绑定能力
4. 会话复用策略配置能力
5. Python 客户端接收器
6. 服务端 WebSocket 主动下发任务能力
7. 客户端本机 Agent 发现与上报能力
8. 支持 macOS / Windows 的 CLI Agent 接入
9. 任务派发记录与执行结果回传能力

### 3.2 二期暂不做

1. GUI 型 Agent 接入
2. 内置 LLM 推理引擎
3. 复杂权限系统
4. 多租户隔离
5. 自动远程桌面控制
6. 完整消息总线替换 WebSocket 网关的高可用架构

## 4. 核心需求拆解

## 4.1 项目管理增强

### 4.1.1 Markdown 文件改为列表管理

当前项目管理里虽然已经有 Markdown 配置，但二期需要进一步明确为“文件列表管理模式”，而不是单纯的配置块编辑。

二期要求：

- 每个项目下有一组 Markdown 文件清单
- 文件清单分为两类：
  - 基础文件
  - 额外文件
- 基础文件至少包括：
  - `AGENTS.md`
  - `SOUL.md`
  - `USER.md`
  - `MEMORY.md`
  - `.learnings/LEARNINGS.md`
- 额外文件可由用户自行添加，例如：
  - `docs/开发规范.md`
  - `docs/部署说明.md`
  - `docs/项目约定.md`

### 4.1.2 文件列表展示要求

项目管理页面中，Markdown 文件应以列表形式展示，至少包含：

- 文件路径
- 文件类型（基础 / 额外）
- 内容摘要
- 更新时间
- 是否参与同步

支持操作：

- 新增额外 Markdown 文件
- 编辑 Markdown 文件
- 删除额外 Markdown 文件
- 查看文件详情
- 按文件单独启用 / 禁用同步

### 4.1.3 同步策略要求

项目级 Markdown 同步策略继续保留，并明确为以下两种：

- `OVERWRITE`
  - 本地已存在同名文件且内容不一致时，直接覆盖
- `CANCEL`
  - 本地已存在同名文件且内容不一致时，取消本次同步并返回冲突信息

二期要求冲突结果必须可追踪，至少记录：

- 哪个项目
- 哪台客户端
- 哪个文件冲突
- 冲突时间
- 冲突策略

## 4.2 需求管理增强

### 4.2.1 需求层级模型

一期的需求模型是单层结构，二期要升级为：

- 总需求
- 子需求

一个总需求下可以有多个子需求。

示例：

- 总需求：支持多智能体分布式协作
  - 子需求1：实现 WebSocket 客户端注册
  - 子需求2：实现服务端主动派发
  - 子需求3：实现会话复用

### 4.2.2 需求层级要求

需求表需要支持以下关系字段：

- 当前需求是否为总需求
- 当前需求的父需求
- 当前需求所属根需求
- 排序号

页面和接口需要支持：

- 创建总需求
- 在总需求下创建子需求
- 查询某个总需求下全部子需求
- 查询某个子需求的上级需求
- 汇总某个总需求下所有子需求进度

### 4.2.3 需求状态聚合

总需求状态不应只手工维护，二期应支持按子需求自动汇总，例如：

- 所有子需求未开始，则总需求为 `PENDING`
- 存在进行中的子需求，则总需求为 `IN_PROGRESS`
- 存在阻塞子需求，则总需求可标记为 `BLOCKED`
- 全部子需求完成，则总需求为 `DONE`

是否允许人工覆盖总需求状态，可以作为二期可配置项，但默认建议系统自动汇总。

---

## 4.3 会话管理

### 4.3.1 为什么要做会话管理

你提出的关键点是：**部分任务希望沿用之前的 Agent 会话，而不是每次新开一个会话。**

这意味着系统不能只管理“任务派发给谁”，还必须管理：

- 这个任务落在哪个会话里
- 这个会话是否可以继续复用
- 这个会话属于哪个 Agent / 哪台电脑 / 哪个需求

### 4.3.2 会话管理能力

二期新增会话管理模块，至少支持：

- 新建会话
- 查询会话列表
- 查看会话详情
- 标记会话状态
- 将需求 / 子需求绑定到会话
- 指定任务派发时的会话策略

### 4.3.3 会话策略

任务下发时，至少支持三种策略：

- `NEW`
  - 为本次任务创建新会话
- `REUSE_SELECTED`
  - 复用用户指定的历史会话
- `REUSE_LATEST`
  - 自动复用该 Agent 最近一次可用会话

### 4.3.4 会话管理关键字段

建议新增会话对象，包含：

- `session_code`
- `session_name`
- `session_type`
- `agent_code`
- `client_code`
- `project_code`
- `requirement_no`
- `root_requirement_no`
- `status`
- `last_active_time`
- `reusable_flag`
- `external_session_id`
- `created_at`
- `updated_at`

说明：

- `external_session_id` 用于映射 Codex CLI / Qoder CLI / Claude Code 自身的会话标识
- `reusable_flag` 用于标记这个会话是否允许继续沿用

## 4.4 新增客户端模块

### 4.4.1 客户端目标

二期需要新增一个 **Python 编写的客户端接收器**。

这个客户端的作用不是做业务页面，而是作为每台电脑上的 Agent 宿主进程，负责：

- 连接服务端
- 保持 WebSocket 长连接
- 接收服务端主动下发的任务
- 上报本机可用智能体
- 调起本机 CLI Agent 执行任务
- 回传执行结果、日志、状态

### 4.4.2 客户端运行平台

首批要求支持：

- macOS
- Windows

不要求 Linux 作为首批强制范围，但设计上应保留可扩展性。

### 4.4.3 客户端首批支持的智能体

二期首批按“CLI 模式”支持以下三类智能体：

- Codex CLI
- Qoder CLI
- Claude Code

要求：

- 只支持 CLI 调用方式
- 客户端需能识别本机是否已安装这些 Agent
- 客户端需上报每个 Agent 的：
  - 名称
  - 类型
  - 版本（如可获取）
  - 是否可用
  - 支持能力标签

---

## 4.5 服务端主动下发任务

### 4.5.1 一期和二期的差异

一期主要是 Agent 轮询拉任务，二期需要增加：

- 服务端主动向客户端推送任务

这意味着服务端需要维护：

- 在线客户端连接
- 客户端与 Agent 的映射
- 任务下发状态
- 投递结果与回执

### 4.5.2 WebSocket 通信要求

二期优先使用 **WebSocket 长连接**，而不是原始 TCP 套接字。

原因：

- 更易维护，不需要自己处理拆包、粘包、消息边界
- Spring Boot 和 Python 两端都有成熟支持
- 文本帧直接传 JSON，调试与日志更直观
- 更轻量，足够满足当前二期的任务派发与状态回传

协议要求：

- 客户端启动后主动建立 WebSocket 连接
- 服务端识别客户端身份
- 连接层支持 `ping/pong`
- 业务层保留心跳消息
- 服务端可主动下发任务消息
- 客户端收到任务后返回接收确认
- 执行完成后返回执行结果

实现建议：

- 首选 WebSocket 原生文本帧 + JSON 消息
- 二期默认不引入 STOMP，先控制复杂度

建议消息类型至少包括：

- `CLIENT_REGISTER`
- `CLIENT_HEARTBEAT`
- `CLIENT_AGENT_REPORT`
- `TASK_DISPATCH`
- `TASK_ACK`
- `TASK_PROGRESS`
- `TASK_RESULT`
- `ERROR_REPORT`

### 4.5.3 任务派发要求

服务端派发任务时，需要明确以下信息：

- 任务归属项目
- 归属总需求 / 子需求
- 指定客户端
- 指定 Agent
- 会话策略
- 是否要求先同步项目 Markdown
- 任务正文
- 优先级
- 超时时间

## 4.6 本机 Agent 发现与上报

客户端需要支持查看“当前电脑有哪些智能体”，因此二期必须新增本机能力扫描机制。

最低要求：

- 扫描 Codex CLI 是否存在
- 扫描 Qoder CLI 是否存在
- 扫描 Claude Code 是否存在
- 上报执行入口命令
- 上报是否可运行

可以扩展的附加字段：

- 默认工作目录
- 支持平台
- 支持会话复用
- 支持的任务类型

## 6. 关键流程设计

## 6.1 流程一：创建总需求并拆分子需求

1. 主控创建总需求
2. 在总需求下创建多个子需求
3. 为每个子需求指定执行 Agent / 客户端 / 会话策略
4. 系统生成可派发任务

输出：

- 总需求
- 子需求列表
- 派发计划

## 6.2 流程二：复用历史会话派发任务

1. 主控选择某个子需求
2. 指定目标 Agent
3. 选择会话策略：
   - 新建
   - 复用指定历史会话
   - 自动复用最近会话
4. 服务端记录派发任务
5. 客户端收到任务并在对应会话中执行

输出：

- 派发记录
- 会话绑定关系
- 执行回传结果

## 6.3 流程三：服务端主动推送任务

1. 客户端启动并建立 WebSocket 连接
2. 客户端注册自身信息与本机 Agent 清单
3. 服务端选择合适客户端和 Agent
4. 服务端推送任务
5. 客户端确认接收
6. 客户端执行
7. 客户端持续回传进度
8. 客户端回传最终结果

## 6.4 流程四：任务执行前同步项目 Markdown

1. 客户端收到任务
2. 根据项目编码拉取项目 Markdown 文件列表
3. 按项目同步策略处理：
   - `OVERWRITE` 直接覆盖
   - `CANCEL` 碰到冲突即取消本次同步
4. 同步成功后开始任务执行
5. 如同步冲突，则回传阻塞原因

## 10. 当前已明确的产品判断

为避免二期方向跑偏，这里把当前明确的判断写死：

1. 需求结构必须从单层升级为树形，不再只支持平铺需求
2. 会话是核心对象，不再只是隐含在 Agent 执行过程中的临时信息
3. 二期必须支持“沿用旧会话”这个操作
4. 服务端必须具备基于 WebSocket 的主动派发能力，不能只依赖轮询
5. 客户端必须使用 Python 编写，首批支持 macOS 和 Windows
6. 首批 Agent 只考虑 CLI 模式，优先支持 Codex CLI、Qoder CLI、Claude Code
7. 项目 Markdown 不只是配置内容，而是需要按文件列表统一管理和同步

## 11. 待确认问题

以下问题当前文档先给出建议，但后续实现前最好再确认：

1. 总需求状态是否完全自动汇总，还是允许人工覆盖
2. 一个子需求是否允许同时绑定多个会话
3. 一个派发任务是否允许多个客户端抢占执行，还是严格单播
4. WebSocket 是否只用于内网环境，还是后续需要考虑公网网关、鉴权与断线重连
5. 客户端本机 Agent 扫描是否需要支持自定义命令路径配置

如果这些问题后续明确，建议再补一版更精确的“二期接口说明”和“二期数据库设计说明”。
